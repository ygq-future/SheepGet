## 1. 目标落点只由一个 interface 给出

- **状态**：已完成（2026-10-28），门禁通过，未提交
- **问题**：`CONTEXT.md` 写明目标落点由后端判定一次，但用户在文件信息窗口切换分类时，界面自己取分类目录、自己判断“路径是否被改过”。内置分类存的是相对子目录（`"Videos"`），界面不做拼装就把它当成保存目录提交；判定“是否改过路径”时又拿绝对路径与相对子目录比较，永远判为已改。
- **证据**：`frontend/src/views/FileInfoView.tsx:489-500`（切换分类直接 `patch({ directory: catDir })`）、`frontend/src/lib/fileInfoDraft.ts:173-188`（绝对路径与分类原始目录做字符串比较）、`internal/config/model.go:249-284`（内置分类存 `Videos` / `Audio` 等相对子目录）、`:765-780`（后端才有拼装规则）、`internal/window/queue.go:1163` 与 `internal/engine/manager.go:1178`（提交与建任务原样保存目录）。
- **实际改动**：
  - `DownloadConfig.ResolveCategoryDestination(categoryID, filename)`：显式分类的落点；分类 id 为空或找不到时退回按文件名命中。`destinationDirectory` 成为“分类目录 + 默认目录”的唯一拼装实现，`ResolveDestination` 与新入口共用。
  - `App.ResolveCategoryDestination` 作为 Wails 绑定暴露；Wails 绑定重新生成（60 个方法，仅 `app.ts` 与窗口模型新增条目）。
  - 文件信息窗口的队列项随附 `CategoryDirectory`（命中分类的已解析默认目录）：登记时给出，探测补齐真名或选定清晰度后随之刷新；手动指定目录不改变它。
  - 前端草稿新增 `categoryDefaultDir`（后端给出的非权威投影），`canKeepCategoryPathOf` 只做一次相等比较，不再读取分类配置、不再比较相对路径。
  - 切换分类改为先向后端要落点再一次性写入分类、目录与默认值；新增序号守卫，连续切换时只让最后一次结果落地（冲突与裁决刷新同样受守卫约束）。
- **验证**（实际执行）：
  - `go test -count=1 ./...`：25 个包、472 项通过；`internal/config` 新增显式分类用例（相对内置目录、绝对自定义目录、未知分类回落、空目录回落），`app_test.go` 新增绑定级用例（内置分类的相对子目录必须落在默认目录之下），`internal/window` 用例断言队列项携带分类默认目录且手动目录不覆盖它。
  - 前端 `bun run typecheck` 与 `bun run test`：13 个文件、116 项通过；`canKeepCategoryPathOf` 用例改为比较后端给出的绝对默认目录，覆盖“相对 `Videos` 与绝对路径误判”的回归。
  - `node scripts/quality-gate.mjs` 全绿（Go 全包、前端测试与构建、扩展 114 项、版本与协议等基建检查）。
- **未做**：不给每个分类下发“已解析目录”清单；不改变提交契约（仍提交分类 id 与最终目录）；没有在原生窗口里逐项点击验收（本机无法自动驱动 Wails 窗口），界面路径由绑定级用例、类型检查与队列契约覆盖。

## 2. 直下载入口与文件信息窗口共用 intake

- **状态**：已完成（2026-10-28），门禁通过，未提交
- **问题**：从链接到任务这条路径实现了两遍。直下载 API 自己复写探测、命名、HLS 选择、落点、占用与重复处理；其中重复链接处理绕过 `duplicate.Decide`，且在队列改为按清晰度去重后仍使用不带清晰度的查找。
- **证据**：`app_loopback.go:141-236`（`directDownload` 全流程）、`app_loopback.go:202`（`FindDuplicateTask`）对比 `internal/window/queue.go:392`、`:738`、`:907`（`FindDuplicateTaskWithVariant`）；时间线：直下载 API 于 `657e919`（2026-10-12）落地，队列的清晰度去重修复 `a5e5115`（2026-10-13）只落在队列侧。
- **范围**（分两步）：
  1. **先做最小修复**：直下载入口按清晰度查找历史任务，使不同清晰度的请求不会被判成同一任务；补一条覆盖该情形的引擎/入口测试。
  2. **再谈结构**：探测 → 命名 → HLS → 目标落点 → 占用 → 裁决 → 提交收进一个 intake 模块，文件信息窗口与直下载入口各自只做请求翻译。提取时必须保留 ADR-0005 决策 1 的约束：引擎调用在队列锁外进行。
- **实际改动**：
  - 新增 `internal/intake`：`Intake` 负责 `Begin`（命名、分类落点、占用、裁决）→ `Probe`（探测，交接已带清晰度时顺手解析）→ `ApplyProbe` → `SelectVariant` / `ApplyVariant` → `StartPreDownload` / `CancelPreDownload` → `Submit`。`Target` 就是一次下载的目标（名字、落点、分类、探测事实与裁决），文件信息窗口的队列项直接嵌入它，窗口不再维护第二份名字与落点。
  - 命名阶梯、HLS 成品名与清晰度标记、分类落点重算、`engine.Occupancy` 的冲突与序号副本、`duplicate.Decide` 的裁决、默认动作为「序号副本」时的改名、提交时按最终落点重新裁决，全部只有这一份实现；`window.QueueController` 只保留顺序、探测/提交/预下载的中间状态与窗口副作用。
  - 直下载入口 `App.directDownload` 收成三段：`Begin`（`ModeDirect`）→ `Probe` → `ApplyProbe` → `Submit`。它不再自己拼名字或决定动作：「没有确认窗口」这一事实作为 `Mode` 交给 intake，需要用户决定的局面取安全答案（历史任务还活着就接着传，已完成就另存副本，无历史且同名成品已存在就取序号副本）。
  - 历史任务查找统一为 `FindDuplicateTaskWithVariant`：登记（用交接带来的清晰度）、探测落地（用已选清晰度）、选定清晰度、提交前各一次；`engine.createTask` 的重复链接兜底也改成同一判定，不再另写一份「只看 URL」的口径——旧口径会把同一清单的第二个清晰度当成重复链接拒绝。
  - 预下载启动改用 `engine.PreDownloadRequest` 并沿用登记时的探测结果（探测失败时不传，让引擎自己再探一次，保留 A03 的失败任务）；提交与预下载的页面地址/分类补齐收进 intake。
  - 删除 `engine.Manager.FindDuplicateTask`（唯一调用方已迁移）、`window.DownloadEngine`（21 个方法）、`window.ErrDuplicateChoiceRequired` 与无人使用的 `window.ErrHLSVariantRequired`；需要用户先选动作的错误改为 `intake.ErrChoiceRequired`。
  - `FileInfoItem` 改为嵌入 `intake.Target`；Wails 绑定重新生成（仍为 60 个方法、33 个模型，JSON 字段集合不变，仅字段顺序与注释来源变化）。
- **验证**（实际执行）：
  - `go test -count=1 ./...`：26 个包、495 项通过。新增 `internal/intake` 22 项（落点与分类、真名补齐后的落点重算、按清晰度查找、直下载的安全默认动作、无历史时的序号副本、窗口模式留给用户决定、清晰度解析与拒绝非清单、探针复用与链接变更失效、提交按最终落点重判、预下载确认与元数据补齐）；`app_test.go` 新增直下载入口用例：同一清单的 720p 与 1080p 得到两条任务、文件名分别为 `master_720p.mp4` / `master_1080p.mp4`，且两条任务的 `Media.Variant.URI` 各是自己那一版。
  - 回归效力已实测：把清晰度从两处历史查找与 `createTask` 兜底里临时去掉后，该入口用例以「两个清晰度落到了同一条任务」失败；恢复后通过。
  - 前端 `bun run typecheck` 与 `bun run test`：13 个文件、116 项通过。
  - `node scripts/quality-gate.mjs` 全绿。
- **未做**：没有把引擎的建任务阶梯本身收敛（序 4 的范围）；没有在原生窗口里逐项点击验收（本机无法自动驱动 Wails 窗口），窗口路径由真实引擎的队列用例、intake 用例与绑定生成结果覆盖。
- **行为变化**：直下载入口现在与窗口共用同一份重复裁决——策略为「跳过并显示完成」时不再静默下载副本，而是返回已有任务；`createTask` 的重复链接兜底按清晰度判定。

## 3. 设置变更走一条应用路径

- **状态**：待办
- **问题**：一次设置变更由 `App` 逐一下推给日志、引擎、环回服务、剪贴板、窗口主题、updater、skill 文件、自启动与端口重启；启动、设置更新、端口重启三条路径各写一遍顺序与回滚。
- **证据**：`app.go:345-388`（`OnSettingsUpdated` 的 10 个落点）、`:399-421`（`UpdateSettings` 的端口重启与回滚）、`:271-285`（启动时的端口比对与持久化）、`:439-466`（`RestartServer`）、`:1037-1057`（`syncSkillFile`）。近期提交密度：`OnSettingsUpdated` 在 2026-09-14 至 10-28 之间被 18 个提交改动。
- **范围**：一个设置应用路径持有“变更 → 各子系统”的映射、顺序与回滚；启动、更新、重启端口调用同一处。不引入事件总线，不改设置模型与绑定面。
- **验收**：三条入口共用同一实现；端口变更失败只在一处回滚；子系统可用假实现断言收到了哪次变更。

## 4. 收敛建任务阶梯

- **状态**：待办
- **问题**：建任务、预下载、重复裁决各有多层同义入口（`AddTask` → `WithHeaders` → `WithMetadata` → `FromProbe` → `FromProbeWithMetadata` 等），调用方必须知道该挑哪一层。序 2 之后窗口不再直接依赖这阶梯（改由 `intake.Engine` 的 13 个方法承载），但阶梯本身仍在：新增一个任务字段仍要在多层包装之间挑位置。
- **证据**：`internal/engine/manager.go:429-439`、`:794-809`、`:1115-1143`（12 个薄包装）；`internal/intake/intake.go` 的 `Engine` 接口（序 2 之后 intake 需要的引擎能力）。
- **范围**：每个动作只留一个入口，变体收进请求结构（引擎里已有 `PreDownloadRequest` 这一先例）；阶梯退回实现内部。不改任务契约与 UI。
- **验收**：`intake.Engine` 的必需方法显著减少（一次建任务、一次预下载、一次重复裁决即可覆盖三处调用）；测试的假引擎不再需要逐个复写全部变体；前端无改动。
- **触发条件**：下一次给任务增加字段或新的元数据来源——那正是阶梯会再长一层的时候。
