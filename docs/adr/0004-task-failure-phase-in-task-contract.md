# 将任务失败阶段写入任务契约，而非从错误文案推断

「下载失败」与「处理失败」是两种不同的用户可见状态，对应两条不同的恢复路径：传输失败可重新传输，处理失败只能复用已下载分片重试处理（ADR-0001）。因此任务必须自带「失败发生在哪个阶段」这一事实，由写入方在失败时记录并持久化，界面据此选择可用操作。

## 决策背景

1. **错误文案不是契约**。任务状态原本只有 `error`，失败发生在传输还是处理只能由界面从错误文本推断（匹配「处理」「mux」「process」等字样）。错误文案来自网络层、文件系统和后续的媒体库，随实现与本地化变化，任何一次文案调整都会静默改变界面行为。
2. **推断失败会给出错误操作**。传输失败的错误文案一旦偶然命中推断字样，界面就会提供「仅重试媒体处理」；而该操作在传输未完成时不成立，用户会以为自己只重跑了处理步骤。
3. **两种重试原本没有行为差异**。重试处理曾直接复用重试下载的实现，使「重试处理」在界面上的承诺与后端行为不一致。Ticket 07 要求处理失败保留分片并支持仅重试处理，这条路径必须在媒体处理落地前就有正确契约，否则该承诺会在实现时被基座反向约束。

## 决策

- 任务契约新增**失败阶段**，取值区分传输与处理；仅当任务处于失败状态时有效，任务重新开始运行时清除。
- 失败阶段的唯一写入方是产生失败的一方：传输失败由下载引擎记录，处理失败由媒体处理层记录。
- 界面据失败阶段选择操作，不读取错误文案；错误文案只作为诊断信息展示。
- **重试下载**拒绝处理阶段失败的任务，避免丢弃已就绪的分片；**重试处理**要求任务确为处理阶段失败。
- 媒体处理尚未接入，因此处理阶段失败与仅重试处理在实现落地前不会被触发；`StatusProcessing` 与处理相关的界面分支保留为已确认的交互边界，不作为媒体功能完成的标记。

## 权衡与约束

- 失败阶段是任务持久化契约的一部分，新增字段需要重新生成前端绑定并与后端同步审阅。
- 该字段不表达失败原因，只表达阶段；具体原因仍由错误文案承载，界面不得据其反推阶段。
- 处理阶段暂时无写入方，其重试入口在媒体处理接入前明确返回不可用，而不是退化为重新下载。
