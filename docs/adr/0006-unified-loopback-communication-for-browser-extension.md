# 浏览器扩展统一本地环回通信架构

## 上下文与核心决策

产品第一版规格（Issue #1 需求 14 及接管时序）要求浏览器扩展与桌面端建立低延迟、双向可靠且支持故障自愈的通信体系。

**决策**：无论便携模式还是安装模式，系统统一采用本地安全 Loopback（HTTP / WebSocket）作为扩展与桌面端之间的唯一通信通道。

## 决策细节

1. **统一本地安全环回通道**：
   桌面端启动时在 `127.0.0.1`（默认端口 `9248`）开启本地 HTTP 服务与 WebSocket 事件总线，随每次启动动态生成高强度随机 Session Token；扩展向桌面端发起配置获取与下载交接请求时，必须通过请求头携带令牌进行鉴权校验。

2. **单一数据来源与端口顺延自愈**：
   扩展内部以持久化存储中的单一目标端口为基准，结合动态顺延探测池（`+0` ~ `+5`）执行主动探针探测；当桌面端因默认端口被占用而自动递增绑定相邻可用端口时，扩展探针在顺延探测命中后立即同步更新持久化目标端口，实现无感自愈连接。

3. **离线安全平滑降级**：
   桌面端支持常驻系统托盘以确保持续提供下载服务；当桌面端未启动或处于离线状态时，浏览器原生下载链路完整保留且不阻断用户正常下载，扩展界面清晰展示就绪状态，待桌面端就绪后自动重连并恢复无感接管。

## 权衡与考量（Considered Options）

- **选项 A（系统原生消息宿主 Native Messaging Host）**：
  早期曾评估作为静默拉起跳板，但在落地实践中存在严重的结构性冲突：
  - **便携模式约束冲突**：注册原生消息宿主必须向操作系统全局注册表（如 Windows `HKCU\Software\Google\Chrome\NativeMessagingHosts`）或固定系统目录写入绝对路径，违背了便携模式（ADR-0003）零注册表侵入与文件目录自包含的硬性要求；
  - **浏览器进程悬挂风险**：Chromium 内核的 `sendNativeMessage` API 缺乏内置超时控制，当宿主进程受外部安全软件拦截或异常时，回调将永久挂起，造成扩展状态机阻塞；
  - **跨平台分发负担**：需为不同操作系统分别维护专属二进制分发与注册/反注册脚本，增加了安装包复杂度。
- **选项 B（浏览器自定义协议 `sheepget://` 唤起）**：
  每次触发均会弹出浏览器系统级模态安全确认框，用户操作体验割裂。
- **选项 C（统一本地 Loopback 通道，本决策采纳）**：
  消除外部辅助进程与系统级配置依赖，安装版与便携版共享完全一致的通信机制，借助端口顺延自愈与状态探测实现高可靠、自包含与跨平台一致的通信拓扑。
