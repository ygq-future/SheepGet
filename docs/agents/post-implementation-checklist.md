# Post-implementation checklist

每次实现完一个功能或缺陷修复、在「交给用户验收」之前，逐条过一遍本清单。它不是 AGENTS.md 里那些原则的复述，而是**可以实际执行的核查动作**——覆盖门禁无法自动判定的问题（重复实现、只写字段、死代码、契约漂移），把架构债拦在提交前。

顺序有意安排：先查最容易漏、也最影响架构质量的三类（重复实现、只写字段、死代码），再查契约一致性，最后才是格式与门禁（有工具兜底，放在末尾）。

---

## 1. 重复实现 —— 每个规则只有一处出处

**动作**：

- 交付前，对本次新增的**每个规则、映射、字符串常量、文件操作**，grep 一遍是否已存在：
  - 同一规则是否在 Go 和 TS 各实现了一份？（尤其「文件名→分类」「URL 取文件名」「重复链接裁决」这类**跨前后端**的规则）
  - 同一个常量/事件名是否已有统一出处？（`config.DefaultConnectionsPerTask`、`internal/protocol`（环回通道与界面事件的线上事实）、`internal/version`（产品版本））
- 跨前后端的规则只在后端实现一次（`config.ResolveDestination`、`internal/duplicate.Decide`），前端只读后端结果，不自行推导。

**判断线索**：一个业务规则的「输入→输出」映射，出现第二次就是该抽的候选；第三次出现就是缺陷。

---

## 2. 只写字段 / 只写参数 —— 写入必须有消费

**动作**：

- 新增 Go 结构体字段、函数参数时，grep 它的**所有读取点**。只找到赋值、找不到消费，就是只写字段。
- 只写字段只有两种归宿：**补上消费端（如果规格要求它生效），或删掉**。不允许「留着以后用」。
- 同理核对前端：新增的 state / prop 是否有真实的渲染或逻辑消费。

**判断线索**：一个字段删掉后测试依然全绿、行为不变，那它现在就是冗余的。

---

## 3. 死代码 —— 替代旧逻辑后，旧路径同步删除

**动作**：

- 本次重构/迁移若「用新实现替代了旧逻辑」，立即搜旧符号的调用点，删干净。
- 检查本次改动是否让某个函数/组件变成孤儿（生产零 import）：
  - TS：`bun run lint` 能报 unused，但**零 import 的导出组件/函数**不会报，要手动查。
  - Go：`unused` / `staticcheck` 能报未导出的，但**被绑定导出、前端却没调用的方法**不会报，重生成绑定后 diff 时要留意。
- 删「样板」时一并清连带引用（配置项、门禁断言等），否则门禁会红。

---

## 4. 魔法值 —— 出现两次就该有名字

**动作**：

- 出现**第二次**的魔法值（数字、字符串）抽成常量；只出现一次的可接受。
- 常量要有单一出处：窗口名/几何 → `appconsts.go`；环回端点、头、端口与事件名 → `internal/protocol`（TS 侧读生成器产出的镜像，不另写字面量）；产品版本 → `build/config.yml`；连接数 → `config.DefaultConnectionsPerTask`。
- **跨进程契约**（事件名、端点路径）抽完后不要靠断言测试钉字面量：两侧各钉一份字面量恰好是漂移的来源。正确做法是让另一侧的取值由生成器产出，再让门禁比较（参考 `scripts/protocol.mjs` 与 stage `protocol`）。

---

## 5. 契约一致性 —— 前后端对同一件事的理解一致

**动作**：

- 改 Go 模型/方法签名后，重新生成绑定：`./.tools/wails3.exe generate bindings -ts ./...`，再看 `git diff --stat frontend/bindings/`，确认只动了该动的模型。
- 新增结构体字段必须重生成（`models.ts` 会重编号）；纯加 `error` 返回的方法签名不变，不必重生成。
- 前后端之间按枚举/词表交互的地方，确认两侧对同一词表的理解一致；后端改了枚举词表，前端要同步。

---

## 6. 测试有效性 —— 断言真实行为

**动作**：

- 写断言前**先读原实现**，按实际行为写，不按「我认为合理的行为」写。
- 测试前提要与断言一致：断言依赖「磁盘有成品文件」，测试就要真的写文件，不能只种内存记录。
- 别用「模拟调用次数」证明正确；用「可观察状态 + 实际输出文件」验证（符合 AGENTS.md 的验收原则）。
- 若断言依赖异步落盘，等待的是**真实字节/状态就绪**，而不是「状态刚翻转就立刻读」。

---

## 7. 行为变化 vs 等价收敛 —— 交付报告里分清

**动作**：

- 交付报告里明确区分「**行为变化**」和「**等价收敛**」两类改动，用「什么操作触发 → 原来怎样 → 现在怎样」描述，不用函数名/行号当标题，不用「同左/同上」。
- 等价收敛不应有行为差异；如果有，说明改错了。

---

## 8. 格式与门禁（最后做，有工具兜底）

- 新增 `.go` 文件必须 `gofmt -w`。
- 改函数名后全局搜调用点再编译——`go build ./...` **不编译测试文件**，漏改调用点要等 `go test` 才暴露。
- 提交前跑完整门禁：`node scripts/quality-gate.mjs`（注意 PATH 需系统 Node 24.21.0，见 quality.md）。
- 门禁报绿但 `go test ./...` 报红时，用 `git worktree add <dir> HEAD --detach` 建干净副本复验，确定是既有失败还是本次引入。
- 完整门禁约 1.5 分钟，用后台运行读 EXIT_CODE，别把超时截断误判成阶段失败。

---

## 使用方式

- 本清单在**每个功能/修复交付验收前**逐条自查，不是事后补救。
- 命中了「判断线索」就停下来改，不要在明知有重复实现/只写字段/死代码时先交付再说「建议另开」。
- 若一条问题确实超出本次任务范围，按 AGENTS.md 的约定：先算工作量，小就直接做掉；做不动的才作为「决策项」提给用户，并给出「选项 / 具体做什么 / 行为变化 / 代价」。
